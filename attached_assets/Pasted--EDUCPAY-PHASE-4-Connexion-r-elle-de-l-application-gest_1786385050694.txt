# EDUCPAY — PHASE 4

## Connexion réelle de l'application + gestion des établissements et année scolaire

Tu es l'agent développeur Full-Stack responsable du projet **EducPAY**, un SaaS de gestion de scolarité destiné aux établissements scolaires.

Les **Phases 1 et 2 sont déjà développées et déployées sur Vercel**.
La base de données est maintenant connectée.

Ta mission dans cette phase est de :

1. auditer et stabiliser l'existant ;
2. supprimer les données fictives/mock utilisées dans les dashboards ;
3. connecter correctement les interfaces aux données réelles ;
4. vérifier et corriger les routes ;
5. vérifier les relations entre les différents éléments ;
6. mettre en place le module **Établissements + Année scolaire** ;
7. faire en sorte que l'application fonctionne correctement en local et sur Vercel ;
8. ne pas casser le design ni les fonctionnalités déjà réalisées.

# 3. SUPPRESSION DES DONNÉES FICTIVES

La base de données étant maintenant connectée, les données fictives utilisées uniquement pour simuler l'application doivent être supprimées.

Rechercher notamment :

* mock data ;
* fake users ;
* fake establishments ;
* fake students ;
* fake payments ;
* fake statistics ;
* tableaux hardcodés ;
* objets statiques utilisés comme données ;
* données de démonstration ;
* valeurs fictives dans les dashboards.

Exemple à supprimer :

```ts
const fakeStudents = [...]
```

ou :

```ts
const dashboardStats = {
  students: 1250,
  payments: 4500000
}
```

si ces données sont censées venir de la base.

IMPORTANT :

Ne supprime pas les composants UI qui utilisent ces données.

Remplace les sources fictives par de vraies sources de données.

---

# 6. MULTI-TENANT : RÈGLE CRITIQUE

EducPAY est un SaaS multi-établissement.

Un établissement ne doit jamais pouvoir accéder aux données d'un autre établissement.

Exemple :

```text
Établissement A
    ↓
users A
school years A
students A
payments A
```

ne doit jamais voir :

```text
Établissement B
    ↓
users B
school years B
students B
payments B
```

Cette isolation doit être assurée côté base de données avec les mécanismes de sécurité appropriés, notamment les politiques RLS lorsque Supabase est utilisé.

NE te contente jamais de masquer les données côté frontend.

# 11. ANNÉE SCOLAIRE

Créer le concept d'année scolaire.

Exemple :

```text
2026-2027
```

Une année scolaire appartient à un établissement.

Relation :

```text
ESTABLISHMENT
      │
      ├── SCHOOL_YEAR 2025-2026
      │
      └── SCHOOL_YEAR 2026-2027
```

Une seule année scolaire peut être active à un instant donné pour un établissement.

Prévoir notamment :

```text
id
establishment_id
name
start_date
end_date
status
created_at
updated_at
```

Les champs exacts doivent rester cohérents avec la base existante.

---

# 12. ANNÉE SCOLAIRE ACTIVE

Chaque établissement doit pouvoir avoir une année scolaire active.

Exemple :

```text
École XYZ

Années scolaires :

2025-2026    CLOSED
2026-2027    ACTIVE
```

Le système doit empêcher qu'un établissement possède simultanément plusieurs années `ACTIVE`.

Cette règle doit être garantie côté base de données lorsque cela est possible.

```text

        ↓
```
