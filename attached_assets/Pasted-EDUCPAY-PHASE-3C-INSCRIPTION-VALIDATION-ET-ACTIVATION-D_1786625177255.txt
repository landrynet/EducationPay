EDUCPAY — PHASE 3C
INSCRIPTION, VALIDATION ET ACTIVATION DES ÉTABLISSEMENTS

==================================================
CONTEXTE DU PROJET
==================================================

EducPAY est un SaaS destiné à la gestion de la scolarité des établissements.

Les phases précédentes sont déjà implémentées et validées :

PHASE 1
→ Structure du projet + Landing Page
→ VALIDÉE

PHASE 2
→ Dashboard Super Admin
→ VALIDÉE

PHASE 3A
→ Création initiale du premier Super Admin
→ VALIDÉE

PHASE 3B
→ Authentification et sécurisation du Super Admin
→ VALIDÉE

Nous sommes maintenant dans :

PHASE 3C
→ Inscription, validation et activation des établissements.

IMPORTANT :
Cette partie doit être développée sans casser les phases précédentes.

==================================================
1. OBJECTIF DE LA PHASE 3C
==================================================

Mettre en place un système permettant à un établissement de :

1. s'inscrire lui-même ;
2. créer les informations de son établissement ;
3. créer son Responsable principal ;
4. configurer les paramètres initiaux nécessaires ;
5. vérifier toutes ses informations ;
6. soumettre sa demande ;
7. attendre la validation du Super Admin ;
8. recevoir un email lorsque la demande est validée ;
9. activer son compte via un lien sécurisé ;
10. définir son mot de passe ;
11. se connecter ensuite à son espace.

Le Super Admin doit pouvoir :

1. recevoir une notification lorsqu'un établissement s'inscrit ;
2. recevoir un email ;
3. consulter la demande ;
4. vérifier les informations ;
5. accepter ;
6. refuser avec un motif ;
7. permettre à l'établissement de corriger sa demande ;
8. conserver l'historique de la demande.

==================================================
4. INSCRIPTION SOUS FORME D'ASSISTANT
==================================================

L'inscription d'un établissement NE DOIT PAS être un énorme formulaire sur une seule page.

Créer un assistant multi-étapes.

Exemple :

ÉTAPE 1
Informations de l'établissement

ÉTAPE 2
Informations du Responsable principal

ÉTAPE 3
Configuration initiale

ÉTAPE 4
Vérification finale

ÉTAPE 5
Soumission

Le nombre exact d'étapes peut être adapté si l'architecture existante le nécessite.

Mais l'expérience doit rester simple et professionnelle.

==================================================
5. INDICATEUR DE PROGRESSION
==================================================

L'assistant doit afficher clairement la progression.

Exemple :

[1 Établissement] — [2 Responsable] — [3 Configuration] — [4 Vérification]

L'utilisateur doit savoir :

- où il se trouve ;
- quelles étapes sont terminées ;
- quelle étape vient ensuite.

Utiliser le Design System existant.

NE PAS créer un composant visuellement différent du reste de l'application.

==================================================
6. ÉTAPE 1 — INFORMATIONS DE L'ÉTABLISSEMENT
==================================================

Collecter uniquement les informations nécessaires.

Exemples :

- nom officiel ;
- type d'établissement ;
- niveaux :
  - Primaire ;
  - Secondaire ;
  - Primaire + Secondaire ;
- adresse ;
- ville ;
- province ;
- téléphone ;
- email officiel ;
- autres informations essentielles définies par le modèle de données.

Créer un identifiant/code établissement automatiquement.

Exemple :

EDU-7F42K9

Le code doit être généré côté système.

L'utilisateur ne doit pas pouvoir choisir un identifiant qui crée un conflit.

==================================================
7. ÉTAPE 2 — RESPONSABLE PRINCIPAL
==================================================

Créer le Responsable principal de l'établissement.

Règles :

1 établissement
→ 1 Responsable principal au départ.

1 Responsable
→ 1 établissement au départ.

Informations possibles :

- prénom ;
- nom ;
- email ;
- téléphone ;
- fonction.

Le Responsable ne doit PAS pouvoir choisir :

SUPER_ADMIN

Le rôle est attribué par le système.

Exemple conceptuel :

role = ESTABLISHMENT_ADMIN

ou le rôle professionnel choisi dans l'architecture existante.

NE PAS permettre au frontend de définir librement le rôle.

==================================================
8. MOT DE PASSE DU RESPONSABLE
==================================================

NE PAS demander au responsable de créer immédiatement son mot de passe définitif pendant la demande si cela entre en conflit avec le système d'activation.

Le compte peut être créé dans un état :

PENDING_ACTIVATION

Après validation de l'établissement :

→ envoyer un lien d'activation.

Le Responsable clique sur le lien.

Il définit alors son mot de passe.

Cette approche évite que l'établissement crée un compte actif avant validation.

==================================================
9. ÉTAPE 3 — CONFIGURATION INITIALE
==================================================

L'établissement doit pouvoir fournir quelques paramètres fondamentaux.

Mais NE PAS transformer l'inscription en configuration complète du système.

Configuration minimale possible :

- année scolaire actuelle ;
- niveau(x) ;
- informations nécessaires au fonctionnement initial.

Ne PAS demander maintenant :

- tous les élèves ;
- tous les parents ;
- tous les comptables ;
- tous les frais détaillés ;
- tous les paiements.

Ces fonctionnalités seront développées dans les phases suivantes.

Après activation, le Responsable pourra compléter la configuration depuis son Dashboard.

==================================================
10. SAUVEGARDE DU FORMULAIRE
==================================================

Le parcours multi-étapes doit être robuste.

Lorsque l'utilisateur passe :

Étape 1
→ Étape 2
→ Étape 3

les informations déjà saisies ne doivent pas disparaître.

Le système doit conserver l'état du formulaire pendant le parcours.

Éviter de faire perdre les données à l'utilisateur lorsqu'il revient en arrière.

==================================================
11. NAVIGATION ARRIÈRE
==================================================

L'utilisateur doit pouvoir revenir à une étape précédente.

Exemple :

Étape 3
→ Retour
→ Étape 2

Il peut modifier les informations.

Puis :

Étape 2
→ Continuer
→ Étape 3

Les données doivent être conservées.

NE PAS forcer l'utilisateur à recommencer depuis le début.

NE PAS attendre uniquement la dernière étape pour détecter toutes les erreurs.

15. SOUMISSION FINALE
==================================================

La page finale doit contenir une action claire :

"Soumettre ma demande"

Avant la soumission :

- vérifier une dernière fois les données ;
- vérifier la cohérence ;
- empêcher les doubles soumissions ;
- afficher un état de chargement.

Après clic :

→ désactiver temporairement le bouton ;
→ envoyer la demande ;
→ gérer correctement les erreurs.

NE PAS créer deux demandes si l'utilisateur double-clique.

==================================================
27. EXPIRATION DU LIEN
==================================================

le lien devient invalide.

Le Responsable doit pouvoir demander :

"Renvoyer le lien d'activation"

Créer un nouveau lien sécurisé.

Invalider correctement l'ancien si nécessaire.

NE PAS permettre l'utilisation indéfinie du même token.

==================================================
30. MULTI-TENANCY
==================================================

C'est une règle CRITIQUE.

Chaque établissement constitue un tenant.

Exemple :

TENANT A
↓
Données A

TENANT B
↓
Données B

Aucune requête utilisateur ne doit permettre à un Responsable de récupérer les données d'un autre établissement.

Le tenant_id / establishment_id doit être correctement utilisé selon l'architecture de données.

NE PAS se fier uniquement à une valeur envoyée par le frontend.

Utiliser les mécanismes serveur + RLS appropriés.
