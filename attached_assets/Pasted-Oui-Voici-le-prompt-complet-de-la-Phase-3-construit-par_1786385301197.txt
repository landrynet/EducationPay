# EDUCPAY — PHASE 3

## Authentification, comptes utilisateurs, rôles, sécurité et isolation multi-établissement

Tu es l'agent développeur Full-Stack senior responsable du projet **EducPAY**, un SaaS de gestion de scolarité destiné aux établissements scolaires.

Les **Phases 1 et 2 sont déjà implémentées et déployées sur Vercel**.

Ta mission dans cette Phase 3 est d'implémenter proprement le système complet d'authentification, d'autorisation et de gestion des comptes, en utilisant l'architecture déjà existante.

---

# 1. OBJECTIF PRINCIPAL

Mettre en place une architecture d'authentification professionnelle, sécurisée et évolutive permettant de gérer les rôles suivants :

```text
SUPER_ADMIN
DIRECTOR
ACCOUNTANT
PARENT
```

L'**élève n'a aucun compte utilisateur**.

Le système doit permettre :

* connexion ;

* création/activation des comptes ;
* gestion des sessions ;
* récupération de mot de passe ;

* gestion des permissions ;
* premier accès sécurisé ;
* audit des actions sensibles ;
* fonctionnement en local ;
* fonctionnement en production sur Vercel + Supabase.

# 4. PRINCIPES D'ARCHITECTURE

L'authentification et l'autorisation doivent être séparées.

```text
Authentication
     ↓
Qui est l'utilisateur ?
     ↓
Authorization
     ↓
Que peut-il faire ?
     ↓
Tenant isolation
     ↓
Dans quel établissement peut-il agir ?
```

Ne jamais considérer qu'un utilisateur est autorisé simplement parce qu'il est authentifié.

# 5. LES TYPES DE COMPTES

EducPAY possède quatre types de comptes utilisateurs.

```text
SUPER_ADMIN
DIRECTOR
ACCOUNTANT
PARENT
```

L'élève :

```text
STUDENT
```

n'est PAS un compte Auth.

Un élève est uniquement une entité métier qui sera développée dans une phase ultérieure.

---

# 6. SUPER ADMIN

## 6.1 Création

Le Super Admin ne possède PAS de page d'inscription publique.

Il ne doit jamais être possible de faire :

```text
/register
role=SUPER_ADMIN
```

Le premier Super Admin doit être créé par une **procédure d'initialisation sécurisée côté serveur**.

Créer un mécanisme d'initialisation dédié, par exemple :

```text
scripts/
   init-super-admin
```

ou une structure équivalente adaptée au projet.

---

# 7. INITIALISATION DU SUPER ADMIN

La procédure doit respecter les règles suivantes :

* exécution côté serveur uniquement ;
* aucun accès depuis le navigateur ;
* aucun endpoint public ;
* aucune clé secrète dans le code ;
* aucun mot de passe codé en dur ;
* aucun secret dans Git ;
* aucun secret dans les logs ;
* utilisation des variables d'environnement ;
* génération cryptographiquement sécurisée des secrets temporaires ;
* procédure contrôlée et documentée ;
* empêcher une réinitialisation accidentelle du compte existant.

Le script doit vérifier si un Super Admin existe déjà.

Si oui :

```text
NE PAS créer automatiquement un deuxième Super Admin.
```

---

# 8. PREMIÈRE CONNEXION DU SUPER ADMIN

Le premier accès doit être considéré comme une activation.

Le compte doit disposer d'un état indiquant que l'activation initiale est obligatoire.

Exemple :

```text
status = FIRST_LOGIN_REQUIRED
```

Lors de la première connexion :

```text
Connexion
   ↓
FIRST_LOGIN_REQUIRED
   ↓
Écran obligatoire de sécurisation
   ↓
Définition des nouveaux identifiants
   ↓
Validation
   ↓
Compte normal
```

Les identifiants temporaires ne doivent plus être utilisables après cette activation.

Le compte réel du Super Admin n'est PAS supprimé.

Seuls les éléments temporaires d'initialisation doivent devenir invalides/inutilisables.

---

# 9. MFA / 2FA SUPER ADMIN

Préparer l'architecture pour l'authentification multifacteur.

Le Super Admin doit être le premier rôle concerné par le MFA.

Si la fonctionnalité MFA de Supabase est disponible dans l'architecture retenue, l'intégrer correctement.

Sinon :

* préparer l'architecture ;
* ne pas inventer un mécanisme cryptographique ;
* documenter clairement ce qui reste à activer.

Le mot de passe seul ne doit pas être considéré comme la protection définitive du Super Admin.

---

# 10. DIRECTEUR

Le Directeur est le responsable principal d'un établissement.

Il est créé à partir de la demande de création d'un établissement.

Flux :

```text
Landing
   ↓
Créer mon établissement
   ↓
Informations responsable
   ↓
Informations établissement
   ↓
Création de la demande
   ↓
PENDING
```

Le responsable possède son propre compte.

Il ne doit pas partager ses identifiants avec les comptables.

---

### Établissement

# 12. STATUT DE LA DEMANDE

Le système doit empêcher l'accès aux fonctionnalités complètes d'un établissement non approuvé.

# 15. COMPTE PARENT

Le parent ne crée pas lui-même son compte dans la première version.

Le compte parent est créé automatiquement lorsque l'établissement ajoute le premier enfant et renseigne le parent.

Règle métier fondamentale :

> Un parent possède un seul compte par établissement.

Un même parent peut avoir plusieurs enfants dans cet établissement.

Exemple :

```text
Parent : Marie Dupont
       │
       ├── Jean Dupont
       ├── Paul Dupont
       └── Sarah Dupont
```

Il n'existe qu'un seul compte parent.

---

# 16. CRÉATION AUTOMATIQUE DU PARENT

Lorsqu'un établissement crée un premier élève :

```text
Créer élève
     ↓
Renseigner parent
     ↓
Parent existe ?
```

### Si NON

```text
Créer compte parent
     ↓
Générer accès temporaire
     ↓
Associer parent ↔ élève
```

### Si OUI

```text
Ne PAS créer un deuxième compte
     ↓
Associer simplement le nouvel élève
```

---

# 17. IDENTIFICATION DU PARENT

La détection d'un parent existant doit utiliser des identifiants fiables.

Priorité recommandée :

```text
Téléphone
Email
```

Le nom seul ne doit jamais suffire pour fusionner automatiquement deux parents.

Si une ambiguïté existe :

```text
PLUSIEURS PARENTS POSSIBLES
        ↓
Demander confirmation à l'établissement
```

Ne jamais associer automatiquement deux personnes uniquement parce qu'elles ont le même nom.

---

# 18. PREMIÈRE CONNEXION DU PARENT

Lors de la création automatique du compte parent :

```text

   ↓

   ↓

   ↓

```

Après activation :

```text
temporary credentials = invalides
```

Le compte parent reste actif.

# 23. RELATION UTILISATEUR / ÉTABLISSEMENT

Les comptes établissement doivent être liés à leur établissement.

```text

 ↓

 ↓

```

```text

```

Le Super Admin est global à la plateforme.

Il n'est pas limité à un établissement.

---

# 24. MULTI-TENANT

EducPAY est multi-établissement.

C'est une règle de sécurité critique.

Exemple :

```text
ESTABLISHMENT A
   ↓
users A
students A
parents A
payments A
```

ne doit jamais pouvoir accéder aux données :

```text
ESTABLISHMENT B
   ↓
users B
students B
parents B
payments B
```

L'isolation doit être assurée au niveau PostgreSQL/RLS.

Ne jamais compter uniquement sur :

```text
if (user.establishment_id === ...)
```

dans le frontend.

---

# 25. RLS

Mettre en place les fondations Row Level Security.

Les politiques doivent être conçues selon :

```text
authenticated user
        ↓
profile
        ↓
role
        ↓
establishment_id
        ↓
authorized data
```

Le Super Admin aura une logique spécifique permettant la gestion globale de la plateforme.

Les utilisateurs d'établissement ne doivent accéder qu'aux données autorisées de leur établissement.

---

# 26. PROTECTION DES ROUTES

Toutes les routes privées doivent vérifier :

1. utilisateur authentifié ;
2. session valide ;
3. rôle autorisé ;
4. établissement autorisé si nécessaire.

Exemple :

```text
/admin/*
    → SUPER_ADMIN

/director/*
    → DIRECTOR

/accountant/*
    → ACCOUNTANT

/parent/*
    → PARENT
```

Respecter les conventions de routing déjà présentes dans le projet.

Un utilisateur ne doit pas pouvoir accéder à une route protégée en tapant directement son URL.
